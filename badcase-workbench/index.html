02 · EVIDENCE GATES

没有稳定复现，不直接讨论训练策略

状态流转由证据驱动，而不是由职级或经验驱动。每个Case都能回答：环境是否一致、哪个变量翻转结果、修复是否泛化。

G0Schema 合法字段完整、权限与脱敏完成
G1稳定复现冻结环境重复运行，记录失败率
G2因果充分单变量实验解释结果翻转
G3修复有效原Case、扩展Case与副作用通过
G4回归就绪能力标签、环境、Verifier完整
REAL CASE · ABSTRACTED

相同触发条件导致步骤节点混淆

生产与本地配置对齐后稳定复现；逐步缩减 System Prompt，定位多个指令使用相同触发条件。唯一化状态表达后结果稳定恢复；跨基座和历史版本验证，确认原始基座即存在问题。

由点到面：扩展触发条件相似度、步骤距离、上下文长度和工具组合，沉淀 instruction_disambiguation 与 long_horizon_routing 能力切片。

控制变量实验设计需要保留的证据
Prompt删除、调序、唯一化触发条件输入哈希 / Token概率
模型基座、历史、当前版本对照模型版本 / 采样配置
环境工具Schema、权限和依赖对照环境快照 / Replay ID
扩展性相邻能力切片与对抗Case通过率 / 副作用 / 置信度
03 · ENGINEERING PARTICIPATION

工程参与，不等于“大家一起看日志”

不同团队将专业知识贡献为插件和实验任务，使判断可重复运行，也让专家从重复排查中释放出来。

04 · DELIVERY PLAN

从轻量标准化开始，再决定是否平台化

首期复用现有日志、Issue和CI，不以建设大平台作为成功标准。

DAY 01—30

定义证据

选定一个高频场景，回放代表性Case并建立现状基线。

  • Case Schema与Taxonomy
  • 状态机、RACI和SLA
  • Top失败类型与等待时间
产物：规范V0.1 + 可运行Demo
DAY 31—60

跑通闭环

接入Replay和首批Validator，形成跨团队Review节奏。

  • ≥30个Case进入标准流程
  • 核心环境复现目标≥95%
  • 首批Benchmark候选注册
产物：Workbench MVP + 报告
DAY 61—90

证明增量

与第30天基线对比，并扩展到第二种问题类型。

  • P0/P1闭环覆盖100%
  • 归因与交付周期可量化改善
  • 形成训练Feature和回归集
产物：V1.0 + 复制模板
EXPECTED OUTCOME

工程同学可以贡献证据，算法同学可以专注判断，Bad Case 可以持续进入模型飞轮。

产品化的终点不是更多字段和页面，而是降低一次可靠归因的组织成本，并保证同一能力缺陷不会在不同项目中被重复发现、重复讨论、重复修复。
