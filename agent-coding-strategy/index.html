CODING DATA STRATEGY · TWO STAGES

从“生成正确代码”
到“完成真实工程任务”

2024 年代码模型的核心，是通过高质量代码语料、仓库上下文、执行验证与任务覆盖，建立可靠的代码生成基础。进入 Agentic Coding 阶段后，策略单元必须从 Instruction → Answer 升级为 Task → Environment → Trajectory → Verifier → Outcome，并围绕长链稳定性、工具调用、失败恢复与单位任务成本优化。

2024 · CODE MODEL问题 → 代码答案正确、可执行、覆盖充分
→
AGENTIC CODING任务 → 环境中的完成态可靠、可恢复、可验证、成本可控
01 · STRATEGY THESIS

不是替换旧策略，而是改变数据的最小闭环

代码知识、语法、算法和生成能力仍是地基；变化发生在任务边界、监督信号、质量标准和评测终点。

保留

代码基础能力

高质量代码预训练、FIM、语言与领域覆盖、执行过滤、修复与测试数据继续作为能力底座。

升级

数据对象

从单轮问答升级为绑定仓库快照、运行环境、工具轨迹、Verifier和最终状态的任务包。

重写

质量定义

“最终答案正确”不再足够，还要检查过程是否稳定、可恢复、安全，并控制Token、时间与工具成本。

闭环

数据决策

不以数据量为终点；用专项能力增益、通用回归、单位有效样本成本决定扩量、改写或停止。

通用大模型代码方向的数据策略

04 · CONCRETE DATA RECIPE

Agent Coding数据到底怎么造

策略不是“多收集轨迹”，而是从能力缺口出发，把真实工程任务改造成可复现、可对照、可验证的训练信号。

能力切片任务构造方法正负监督信号Verifier与训练出口
01

仓库检索与定位

找对文件、符号和依赖

从已合并Issue/PR抽种子，将仓库回退至修改前Commit，只暴露Issue与必要约束，隐藏原Patch；用实际改动文件和调用链生成Gold Evidence。

正：关键文件召回充分、上下文精简。
负：定位错文件、漏依赖、无关读取过多。

验证：Evidence Recall、编辑范围、最终测试。
SFT示范 + DPO检索偏好

02

工具调用与状态跟踪

会选工具，也会读结果

选取必须经过Search、Build、Test、API或MCP才能完成的任务；固定工具Schema与初始状态，记录每次Observation、参数、返回值和状态变化。

正：参数合法、顺序合理、根据返回结果推进。
负：Schema错误、重复调用、忽略报错或状态已变。

验证：Schema校验、状态机、工具结果一致性。
SFT + 局部决策DPO

03

跨文件工程修改

不是只写一个函数

从真实Bug修复、功能PR、依赖升级和重构中生成任务；冻结仓库镜像，隐藏部分测试，将测试目录设为只读并限制允许修改的文件范围。

正：最小充分Patch，全量回归通过。
负：改测试、硬编码、扩大改动或制造副作用。

验证：目标测试 + 隐藏测试 + Diff Policy。
SFT成功轨迹 + RLVR任务

04

失败诊断与恢复

长链任务的核心增量

在固定步骤注入编译失败、测试失败、工具超时、权限不足、错误依赖或错误假设；同一任务采样“恢复成功”和“重复失败”两类轨迹。

正：识别原因、更新假设、回退并重规划。
负：盲目重试、无效循环、状态丢失。

验证：故障识别率、恢复成功率、循环率。
SFT恢复示范 + DPO/RLVR

05

长程规划与约束

多阶段完成而非一次生成

构造需要“理解需求—定位—修改—测试—复核”的多阶段任务，并加入禁止项、时间/Token预算、审批边界和中间里程碑。

正：计划随证据更新，关键约束全程保持。
负：计划与执行脱节、提前结束或越权。

验证：里程碑状态、约束遵循、端到端完成率。
课程SFT + 可验证RLVR

06

视觉与前端任务

把“看起来对”变成可判定

以设计稿、页面截图、交互说明和现有前端仓库组成任务包；设置多视口、关键交互、可访问性和视觉回归基线。

正：结构、视觉、交互与工程约束同时满足。
负：只拟合截图、交互失效或破坏响应式。

验证：DOM/交互测试 + Visual Diff + A11y。
SFT + 多目标RLVR

ONE ITERATION

一轮数据策略如何落地

每轮只解决一个可衡量的能力缺口，以对照实验决定扩量，而不是先设大规模生产目标。

  1. 定切片基线评测找Top失败类型，定义成功、失败与停止条件。
  2. 造任务抽取真实种子，冻结Repo/环境，构建独立Verifier。
  3. 采轨迹跨模型、温度和Agent框架Rollout，保留成功、恢复与失败。
  4. 做配对控制任务与环境不变，只保留单一关键决策差异。
  5. 训与验按缺陷路由SFT/DPO/RLVR，并同时看专项、通用与成本。
  6. 调配比根据单位千条有效轨迹的能力增益决定扩量、改写或停止。
40%直接成功轨迹压缩冗余步骤，作为SFT行为范式
25%失败后恢复成功保留诊断—重规划—验证的关键转折
20%同任务偏好对只比较一个可归因的局部决策
15%诊断型困难负例进入DPO、Critic或回归集，不直接模仿

以上是同一能力桶内的首轮轨迹用途配比，与下一节“任务类型组合”是两个维度；前者决定怎么学，后者决定学什么。比例只作为消融起点。

05 · STEP AGENT PORTFOLIO

面向阶跃 Agent Coding 的首轮数据组合

公开信号显示，阶跃当前重点覆盖长上下文、高可靠工具调用、长程编排、多模态理解与高吞吐生产任务。数据组合应围绕这些能力建立可验证任务，而不是单纯堆积长CoT。

30%

仓库级工程任务

Issue → 定位 → 跨文件修改 → 测试通过；覆盖Bug修复、功能开发、依赖升级和重构。

SWE-like · Multi-file · Patch
20%

终端与工具任务

构建、部署、数据处理、脚本编排、API与MCP调用，强调Schema正确和状态一致。

Terminal · Tool Use · MCP
15%

上下文检索与规划

在长仓库中找对文件、证据和依赖，控制无关上下文，验证计划与执行的一致性。

256K · Retrieval · Plan
15%

失败恢复轨迹

编译失败、测试失败、权限不足、工具超时、错误假设后的诊断、回退与重规划。

Debug · Retry · Recovery
10%

视觉与多模态开发

UI截图理解、设计稿转实现、视觉回归和图表/文档驱动的代码任务。

Vision · UI · Multimodal
10%

安全、效率与协作

只读计划、审批边界、最小改动、并行Agent交接与成本约束下的任务完成。

Policy · Cost · Handoff

配比口径：Agent后训练实验池的任务数；首轮保持总任务难度、环境成本与Verifier类型可对照。通过分桶消融，以“专项成功率增益 / 每千条有效轨迹成本”滚动调整，而非一次性固化。

06 · DATA FACTORY

从任务种子到可训练资产的八道门

数据管线的核心价值，是让任务真的可做、结果真的可判、轨迹真的可学，并保留每次筛选和改写的血缘。

任务种子

真实Issue/PR、终端任务、产品Case与定向合成。

输出：Task Spec

环境固化

锁定Commit、依赖、镜像、权限、工具版本和初始状态。

门槛：复现率 ≥ 95%

Verifier构建

测试、Lint、状态、性能、安全和副作用联合判定。

门槛：确定性 ≥ 98%

可解性校验

专家或参考Agent确认任务信息充分、答案非唯一也可判。

输出：Gold Evidence

多策略Rollout

跨模型、温度和Agent框架采样成功、失败与恢复轨迹。

输出：Trajectory Set

轨迹质检

过滤偶然成功、伪工具调用、无效循环、泄漏和奖励投机。

输出：Quality Score

归因与路由

识别知识、规划、工具、恢复或工程问题，选择训练出口。

输出：Capability Tag

注册与回归

绑定数据、模型、Prompt、环境、评测与实验版本。

输出：Dataset Card
QUALITY GATES

准入不是一个总分，而是四个不可互相抵消的门槛

G1 · 可复现

同镜像重复运行；环境差异可解释。

G2 · 可验证

Verifier独立、确定、无答案泄漏。

G3 · 可学习

关键决策清楚；无冗余循环与伪因果。

G4 · 可治理

许可证、隐私、污染、血缘与版本完整。

07 · TRAINING & EVALUATION

先判断缺陷，再选择训练出口

同一个失败现象可能来自模型、数据、Agent框架或运行环境。训练方案必须由因果证据决定，不能把所有Bad Case都改写成SFT。

知识与代码分布缺口

继续预训练

新框架、低资源语言、仓库结构和领域代码覆盖不足。

看：困惑度 / 补全 / 语言切片
正确行为范式缺失

SFT

稳定、高质量、可复现的规划、工具使用与失败恢复示范。

看：模仿后专项成功率
方案优劣边界不清

DPO / 偏好学习

同任务下存在可归因的局部决策差异，如工具、检索或Patch质量。

看：Pair准确率 / 泛化
长链探索与决策问题

RLVR

环境可复现、奖励可验证、存在多条解题路径的仓库或终端任务。

看：Pass^k / 稳定性 / Reward
系统和接口缺陷

工程修复

Prompt、Tool Schema、Router、权限、超时、重试和上下文管理问题。

看：修复后回归与副作用
EVALUATION STACK

四层评测，避免“榜单上涨但生产不可用”

每次数据实验同时观察目标能力、通用回归与生产效率；只有三者同时满足门槛，才进入扩量。

L1 · 基础代码

LiveCodeBench类、编译率、单测、FIM、语言与领域切片。

L2 · Agent原子能力

检索命中、工具参数、状态跟踪、约束遵循、错误识别与恢复。

L3 · 端到端任务

SWE-bench / SWE-bench Pro类、Terminal-Bench类及内部仓库任务。

L4 · 生产指标

首轮成功率、Pass^k、人工接管率、回滚率、时延、Token与工具成本。

GO / ADJUST / STOP

扩量决策公式

专项能力有显著增益 + 通用回归不退化 + 环境与Verifier可信 + 单位有效样本成本可接受。

Data ROI专项成功率增益÷千条有效轨迹成本按能力切片比较，而不是只看总体均分
WHY THIS FITS STEPFUN · PUBLIC SIGNALS

公开能力指向同一个数据核心：长上下文中的可靠感知、工具编排、工程执行与结果验证。

Step 3.7 Flash公开支持256K上下文和原生多模态，并强调生产级Agent、外部API与长程工作流；官方结果包括SWE-Bench PRO 56.3、Terminal-Bench 2.1 59.5。Step 3.5 Flash公开结果包括SWE-bench Verified 74.4与Terminal-Bench 2.0 51.0。Step Realtime CLI则展示了仓库阅读、文件修改、命令执行、会话续接与只读规划等实际Coding Agent交互。由此推导的数据优先级是：真实仓库环境、工具轨迹、失败恢复、独立Verifier和成本约束。

Step 3.7 Flash ↗ Step 3.5 Flash ↗ Step Realtime CLI ↗ SWE-bench ↗
代码数据策略的终点，不是拥有更多轨迹，而是持续生产“可复现、可验证、可归因、能带来模型增益”的任务资产。
